Understanding a SYN flood incident

Course exerciseTCP · Incident reporting

The exercise describes a website becoming unavailable while a server receives many connection requests that do not complete the TCP handshake.

Summary

The original report describes a high volume of SYN packets from 203.0.113.0 to 192.0.2.1, SYN-ACK replies, and missing final ACKs. This pattern is consistent with the SYN flood scenario presented in the course.

The write-up explains the mechanism. It does not independently establish an attack rate, identify the sender, or measure server resource exhaustion.

Where the handshake stops

StepNormal connectionReported pattern
1 · SYNClient requests a connection.Many requests arrive.
2 · SYN-ACKServer acknowledges and responds.The server sends replies.
3 · ACKClient acknowledges, completing the handshake.The final acknowledgements are reported missing.

Depending on the server's implementation and defenses, incomplete connections can consume connection-tracking or backlog capacity. Legitimate clients may then experience connection delays or timeouts.

What would strengthen the finding

  • A packet capture with a defined time window and capture location.
  • Counts of SYN requests, completed handshakes and retransmissions, compared with normal traffic.
  • Server metrics showing backlog pressure or dropped connections during the same period.
  • Checks for packet loss, asymmetric visibility and other reasons that ACK packets might be absent from a capture.

A source address in captured traffic is not sufficient to identify a person or prove distributed origins.

Possible response

Review supported SYN flood protections, connection limits and upstream filtering with the service owner. Any change should be evaluated against legitimate traffic and monitored for impact.

These are proposed response considerations. No mitigation was deployed or tested as part of this report.
